Bifrost's plugin system lets you intercept requests and responses at multiple points in the gateway pipeline without touching provider configuration or application code. Plugins are compiled Go shared objects (`.so` files) that load at runtime, run in-process, and share Bifrost's full type system with zero IPC overhead.

## What plugins can do

Plugins give you middleware hooks around every LLM call:

- **Transform requests and responses** — modify, enrich, or redact data before it reaches a provider or after it returns
- **Add custom validation** — enforce business rules, content policies, or schema checks
- **Implement custom caching** — serve responses from any external store based on custom logic
- **Integrate with external systems** — forward logs, traces, or analytics to any platform
- **Mock provider responses** — return deterministic test responses without hitting real APIs

## Plugin lifecycle and hooks

When a request flows through Bifrost, plugins are invoked at specific points in this order:

<Steps>
  <Step title="HTTPTransportPreHook">
    Runs before the request enters Bifrost core. Intercept raw HTTP headers and body. HTTP transport only.
  </Step>
  <Step title="PreRequestHook (v1.6.x+)">
    Runs **once per request** before any provider attempt. Use this hook to make routing decisions — choose provider, model, or override the fallback chain. Decisions propagate to every retry and fallback.
  </Step>
  <Step title="PreLLMHook">
    Runs per provider attempt, in registration order. Can short-circuit the request and return a response directly (without calling the provider).
  </Step>
  <Step title="Provider call">
    Bifrost forwards the request to the selected provider (skipped if a PreLLMHook short-circuited).
  </Step>
  <Step title="PostLLMHook">
    Runs per provider attempt, in **reverse** registration order. Receives the full response for enrichment or logging.
  </Step>
  <Step title="HTTPTransportPostHook">
    Runs after Bifrost returns the response. HTTP transport only, reverse order.
  </Step>
</Steps>

<Note>
  Dynamic plugins require a dynamically-linked Bifrost binary, which is not enabled by default. See [Building Dynamically Linked Bifrost Binary](https://docs.getbifrost.ai/plugins/building-dynamic-binary) to enable it.
</Note>

## Managing plugins via the REST API

Bifrost exposes a full CRUD API for plugin management. All changes take effect immediately without a restart.

### Create a plugin

```bash
curl -X POST http://localhost:8080/api/plugins \
  -H "Content-Type: application/json" \
  -d '{
    "name": "my-custom-plugin",
    "enabled": true,
    "path": "/path/to/myplugin.so",
    "config": {
      "some_option": "value"
    }
  }'
```

### List all plugins

```bash
curl http://localhost:8080/api/plugins
```

```json Response
[
  {
    "name": "semantic_cache",
    "enabled": true,
    "path": "",
    "config": {
      "provider": "openai",
      "embedding_model": "text-embedding-3-small",
      "dimension": 1536,
      "ttl": "5m",
      "threshold": 0.8
    }
  },
  {
    "name": "my-custom-plugin",
    "enabled": true,
    "path": "/path/to/myplugin.so",
    "config": { "some_option": "value" }
  }
]
```

### Get a specific plugin

```bash
curl http://localhost:8080/api/plugins/semantic_cache
```

### Update a plugin

```bash
curl -X PUT http://localhost:8080/api/plugins/my-custom-plugin \
  -H "Content-Type: application/json" \
  -d '{
    "enabled": false,
    "path": "/path/to/myplugin.so",
    "config": { "some_option": "updated-value" }
  }'
```

### Delete a plugin

```bash
curl -X DELETE http://localhost:8080/api/plugins/my-custom-plugin
```

## Built-in plugin: Mocker

The **Mocker plugin** is a first-party plugin that intercepts LLM requests and returns configurable mock responses — no real provider calls made. It's invaluable for CI pipelines, integration tests, and load testing scenarios where you need deterministic, cost-free responses.

### How the Mocker plugin works

The mocker evaluates a list of **rules** in priority order. Each rule specifies:
- **Conditions** — which providers, models, or message content to match
- **Probability** — how often to activate (0.0 = never, 1.0 = always)
- **Responses** — one or more possible responses (with optional weights for random selection)
- **Latency** — optional simulated delay to mimic real provider behaviour

When no rules match, the `DefaultBehavior` setting controls what happens: `"passthrough"` (real provider call), `"success"` (default mock), or `"error"`.

### Enabling the Mocker plugin

Create the mocker plugin via the API with your rule configuration:

```bash
curl -X POST http://localhost:8080/api/plugins \
  -H "Content-Type: application/json" \
  -d '{
    "name": "mocker",
    "enabled": true,
    "path": "",
    "config": {
      "enabled": true,
      "default_behavior": "passthrough",
      "rules": [
        {
          "name": "openai-catch-all",
          "enabled": true,
          "priority": 10,
          "probability": 1.0,
          "conditions": {
            "providers": ["openai"]
          },
          "responses": [
            {
              "type": "success",
              "weight": 1.0,
              "content": {
                "message": "This is a mock response from OpenAI.",
                "usage": {
                  "prompt_tokens": 15,
                  "completion_tokens": 12,
                  "total_tokens": 27
                }
              }
            }
          ]
        }
      ]
    }
  }'
```

### Mocker rule reference

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `name` | string | — | Unique rule name |
| `enabled` | bool | `true` | Enable or disable this rule |
| `priority` | int | `0` | Higher numbers evaluated first |
| `probability` | float | `1.0` | Activation probability: `0.0` = never, `1.0` = always |
| `conditions.providers` | string[] | — | Match specific providers, e.g. `["openai"]` |
| `conditions.models` | string[] | — | Match specific models |
| `conditions.message_regex` | string | — | Regex pattern matched against message content |
| `responses[].type` | string | — | `"success"` or `"error"` |
| `responses[].weight` | float | `1.0` | Relative weight for random selection |
| `responses[].content.message` | string | — | Static response text |
| `responses[].content.message_template` | string | — | Template with `{{provider}}`, `{{faker.*}}` etc. |
| `responses[].allow_fallbacks` | bool\|null | `null` | `false` to block fallback chain on this error |
| `latency.type` | string | — | `"fixed"` or `"uniform"` |
| `latency.min_ms` | int | — | Fixed delay or minimum uniform delay in ms |
| `latency.max_ms` | int | — | Maximum uniform delay in ms |

## Building your own plugin

If you need behaviour beyond what built-in plugins provide, you can write a Go plugin compiled as a shared object:

```bash
# Build your plugin as a shared object
go build -buildmode=plugin -o myplugin.so ./plugins/myplugin/

# Load it at runtime via the API
curl -X POST http://localhost:8080/api/plugins \
  -H "Content-Type: application/json" \
  -d '{
    "name": "myplugin",
    "enabled": true,
    "path": "/path/to/myplugin.so",
    "config": {}
  }'
```

Your plugin must export these functions matching Bifrost's interface:

```go myplugin/main.go
package main

func Init(config any) error         { /* initialize */ return nil }
func GetName() string               { return "myplugin" }
func PreLLMHook() /* ... */         { /* modify request */ }
func PostLLMHook() /* ... */        { /* inspect response */ }
func Cleanup() error                { return nil }
```

<Warning>
  Go plugins are **Linux and macOS only** — no Windows support. The plugin and Bifrost binary must be built with the same Go version and target architecture. Cross-compilation is not supported.
</Warning>

Bifrost Guardrails validate every LLM request and response against your content policies before they reach your models or your users. You define **Rules** (the conditions under which validation runs, expressed in CEL) and **Profiles** (the provider configurations that perform the actual evaluation). Rules reference one or more Profiles, so you can layer multiple providers for defense-in-depth—for example, running AWS Bedrock PII detection and Patronus hallucination checks on the same request.

<Note>
  Guardrails are an Enterprise feature. Activate them from **Guardrails → Configuration** in the Bifrost dashboard.
</Note>

## Core concepts

Guardrails are built around two objects that work together:

- **Rules** define *when* and *what* to validate using a [CEL](https://cel.dev/) expression. A rule targets `input`, `output`, or `both` and can reference multiple Profiles for layered evaluation.
- **Profiles** define *how* content is evaluated—provider credentials, endpoints, thresholds, and detection settings. Profiles are reusable across multiple Rules.

### Streaming behavior

When an output guardrail is active on a streaming response, Bifrost accumulates the full response before running evaluation. If the content passes, Bifrost forwards it to the client. If it is blocked or modified, Bifrost applies that result instead. This adds latency equal to the model's generation time plus guardrail evaluation time.

<Warning>
  GraySwan Cygnal is a text-only streaming exception: Bifrost sends text chunks directly to the client without forwarding them to Cygnal. If the same rule also includes another output-guardrail profile, Bifrost still waits for that profile to evaluate the completed response before it is returned to the client.
</Warning>

## Configuring a profile

Profiles are managed at `/api/guardrails/{provider}` where `{provider}` is one of `secrets`, `regex`, `bedrock`, `azure`, `model-armor`, `crowdstrike-aidr`, `grayswan`, or `patronus-ai`.

<CodeGroup>
```json AWS Bedrock
{
  "provider_name": "bedrock",
  "policy_name": "PII Detection Profile",
  "enabled": true,
  "config": {
    "access_key": "env.AWS_ACCESS_KEY_ID",
    "secret_key": "env.AWS_SECRET_ACCESS_KEY",
    "guardrail_arn": "arn:aws:bedrock:us-east-1:123456789:guardrail/abc123",
    "guardrail_version": "1",
    "region": "us-east-1"
  }
}
```

## Creating a rule via API

```bash
curl -X POST http://localhost:8080/api/guardrails/rules \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Block PII in Prompts",
    "description": "Prevent PII from being sent to LLM providers",
    "enabled": true,
    "celExpression": "request.messages.exists(m, m.role == \"user\")",
    "applyTo": "input",
    "samplingRate": 100,
    "timeout": 5000,
    "selectedGuardrailProfiles": ["regex:1", "bedrock:2"]
  }'
```

<Note>
  The HTTP API uses camelCase field names (`celExpression`, `applyTo`, `samplingRate`). Profiles are referenced as `"<provider-type>:<config-id>"` strings, for example `"regex:1"` or `"patronus-ai:6"`.
</Note>

### CEL expression examples

Rules use [Common Expression Language](https://cel.dev/) to describe when validation should fire.

```cel
# Always apply this rule
true

# Apply only to user messages
request.messages.exists(m, m.role == "user")

# Apply to messages containing sensitive keywords
request.messages.exists(m, m.content.contains("confidential"))

# Apply only to GPT-4 family models
request.model.startsWith("gpt-4")

# Apply to long prompts (>1000 chars total from user)
request.messages.filter(m, m.role == "user").map(m, m.content.size()).sum() > 1000

# Combine multiple conditions
request.model.startsWith("gpt-4") && request.messages.exists(m, m.role == "user" && m.content.size() > 500)
```

## Attaching guardrails to requests

Once you have a rule configured, you can enforce it on any request using the `x-bf-guardrail-id` header or the `bifrost_config` body field.

<CodeGroup>
```bash Single guardrail (header)
curl -X POST http://localhost:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "x-bf-guardrail-id: bedrock-prod-guardrail" \
  -d '{
    "model": "gpt-4o-mini",
    "messages": [{"role": "user", "content": "Help me with this task"}]
  }'
```

```bash Multiple guardrails (header)
curl -X POST http://localhost:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "x-bf-guardrail-ids: bedrock-prod-guardrail,azure-content-safety-001" \
  -d '{
    "model": "gpt-4o-mini",
    "messages": [{"role": "user", "content": "Help me with this task"}]
  }'
```

```bash Inline body config
curl -X POST http://localhost:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-4o-mini",
    "messages": [{"role": "user", "content": "Help me with this task"}],
    "bifrost_config": {
      "guardrails": {
        "input": ["bedrock-prod-guardrail"],
        "output": ["patronus-ai-001"],
        "async": false
      }
    }
  }'
```
</CodeGroup>

## Best practices

<AccordionGroup>
  <Accordion title="Organize profiles by purpose">
    Create separate profiles for different concerns—one for PII, one for content filtering, one for secrets detection. Use clear policy names like `"PII Detection - Bedrock"` rather than `"Profile 1"`. Store all credentials in environment variables, never hardcoded.
  </Accordion>
  <Accordion title="Layer providers for defense-in-depth">
    Link multiple profiles to a single rule for comprehensive coverage. For example, pair Bedrock (PII + content) with Patronus (hallucination) for output rules on customer-facing applications.
  </Accordion>
  <Accordion title="Use sampling rates on high-traffic endpoints">
    Set `samplingRate` to a percentage less than 100 on rules where latency is critical. Start at 100% to baseline behavior, then reduce as confidence grows.
  </Accordion>
  <Accordion title="Set tight timeouts">
    Each guardrail evaluation adds latency. Set `timeout` to a value appropriate for your SLA—typically 2,000–5,000 ms for synchronous flows.
  </Accordion>
</AccordionGroup>

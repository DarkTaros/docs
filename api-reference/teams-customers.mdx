---

Bifrost's governance model supports a three-level hierarchy: **customers** sit at the top, **teams** sit in the middle, and **virtual keys** sit at the bottom. Each level carries its own independent budget, and all budgets in a request's chain are checked simultaneously — a request is rejected if any ancestor budget is exceeded. Rate limits, however, are only supported at the virtual key level.

```
Customer  ──  top-level organization or tenant, owns an optional spend budget
  └── Team  ──  department or project group, owns an optional spend budget
        └── Virtual Key  ──  individual access token, owns budgets + rate limits
```

<Note>
  All management endpoints require `Authorization: Bearer <admin-api-key>`. Virtual keys and `x-api-key` headers are not accepted on management routes.
</Note>

## Customers

### Create a customer

<Note>
  `POST /api/governance/customers`
</Note>

Creates a new customer. Customers represent the highest tier in the governance hierarchy — typically an organization, external tenant, or major business unit. Teams and virtual keys can be assigned to a customer to inherit its budget ceiling.

#### Request body

<ParamField body="name" type="string" required>
  Display name for the customer.
</ParamField>

<ParamField body="budget" type="object">
  Optional organization-wide spend budget.

  <Expandable title="budget fields">
    <ParamField body="max_limit" type="number" required>
      Maximum USD spend allowed. When exceeded, all requests from any key under this customer return `402`.
    </ParamField>
    <ParamField body="reset_duration" type="string" required>
      How often the budget resets. Accepted values: `1m`, `1h`, `1d`, `1w`, `1M`, `1Y`.
    </ParamField>
    <ParamField body="calendar_aligned" type="boolean" default="false">
      When `true`, resets at UTC calendar boundaries instead of on a rolling window.
    </ParamField>
  </Expandable>
</ParamField>

#### Example

<CodeGroup>
```bash cURL
curl -X POST https://your-bifrost-host/api/governance/customers \
  -H "Authorization: Bearer <admin-api-key>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Acme Corporation",
    "budget": {
      "max_limit": 2000.00,
      "reset_duration": "1M",
      "calendar_aligned": true
    }
  }'
```

```json Response 200
{
  "message": "Customer created successfully",
  "customer": {
    "id": "cust_acme001",
    "name": "Acme Corporation",
    "budget_id": "bgt_cust_001",
    "budget": {
      "id": "bgt_cust_001",
      "max_limit": 2000.00,
      "reset_duration": "1M",
      "current_usage": 0.00,
      "calendar_aligned": true,
      "last_reset": "2024-07-01T00:00:00Z",
      "created_at": "2024-07-01T09:00:00Z",
      "updated_at": "2024-07-01T09:00:00Z"
    },
    "teams": [],
    "virtual_keys": [],
    "created_at": "2024-07-01T09:00:00Z",
    "updated_at": "2024-07-01T09:00:00Z"
  }
}
```
</CodeGroup>

#### Response fields

<ResponseField name="message" type="string">Status message.</ResponseField>
<ResponseField name="customer" type="object">
  The newly created customer.

  <Expandable title="customer fields">
    <ResponseField name="id" type="string">Unique customer ID.</ResponseField>
    <ResponseField name="name" type="string">Display name.</ResponseField>
    <ResponseField name="budget_id" type="string">ID of the attached budget record, or `null`.</ResponseField>
    <ResponseField name="budget" type="object">Full budget record with current usage.</ResponseField>
    <ResponseField name="teams" type="array">Teams belonging to this customer.</ResponseField>
    <ResponseField name="virtual_keys" type="array">Virtual keys directly attached to this customer.</ResponseField>
    <ResponseField name="created_at" type="string">ISO 8601 creation timestamp.</ResponseField>
    <ResponseField name="updated_at" type="string">ISO 8601 last-updated timestamp.</ResponseField>
  </Expandable>
</ResponseField>

## Teams

### Create a team

<Note>
  `POST /api/governance/teams`
</Note>

Creates a new team. Teams provide department-level budget grouping beneath a customer. Multiple virtual keys can belong to a team, inheriting its budget ceiling. Note that teams cannot have rate limits — rate limits are enforced at the virtual key level only.

#### Request body

<ParamField body="name" type="string" required>
  Display name for the team.
</ParamField>

<ParamField body="customer_id" type="string">
  Optional customer this team belongs to. When set, the team's budget is checked alongside the customer budget on every request.
</ParamField>

<ParamField body="budget" type="object">
  Optional department-level spend budget.

  <Expandable title="budget fields">
    <ParamField body="max_limit" type="number" required>
      Maximum USD spend. When exceeded, all keys under this team return `402`.
    </ParamField>
    <ParamField body="reset_duration" type="string" required>
      Reset period, e.g. `1M` for monthly.
    </ParamField>
    <ParamField body="calendar_aligned" type="boolean" default="false">
      Reset at UTC calendar boundaries when `true`.
    </ParamField>
  </Expandable>
</ParamField>

#### Example

<CodeGroup>
```bash cURL
curl -X POST https://your-bifrost-host/api/governance/teams \
  -H "Authorization: Bearer <admin-api-key>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Engineering",
    "customer_id": "cust_acme001",
    "budget": {
      "max_limit": 500.00,
      "reset_duration": "1M",
      "calendar_aligned": true
    }
  }'
```

```json Response 200

      "max_limit": 500.00,

      "current_usage": 0.00,
      "calendar_aligned": true,
      "last_reset": "2024-07-01T00:00:00Z"
    },
    "virtual_keys": [],
    "created_at": "2024-07-01T09:05:00Z",
    "updated_at": "2024-07-01T09:05:00Z"
  }
}
```
</CodeGroup>

#### Response fields

<ResponseField name="message" type="string">Status message.</ResponseField>

  The newly created team.

  <Expandable title="team fields">

    <ResponseField name="budget_id" type="string">Attached budget record ID, or `null`.</ResponseField>

## Hierarchy and budget enforcement

When Bifrost receives a request authenticated with a virtual key, it evaluates all budgets in the ancestry chain simultaneously:

1. **Virtual key budget** — checked first, closest to the request
2. **Team budget** — checked if the key belongs to a team
3. **Customer budget** — checked if the key or its team belongs to a customer

If any budget is exceeded, the request is rejected with `402 Payment Required` and a message identifying which budget was breached. All budgets are independent — reaching the team limit does not reset the virtual key's own budget.

<Tip>
  Assign virtual keys to teams (rather than directly to customers) when you need sub-organization cost tracking. Use direct customer attachment for executive or service-account keys that span multiple departments.
</Tip>

## Error responses

| Status | Type | Description |
|--------|------|-------------|
| `400` | `bad_request` | Missing required field or invalid value |
| `402` | `budget_exceeded` | Spend budget exceeded at any hierarchy level |
| `404` | `not_found` | Customer or team ID does not exist |
| `500` | `internal_error` | Unexpected server error |
